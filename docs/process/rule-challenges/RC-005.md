# RC-005 — the gate bypass let a regime change merge with its tests unrun
- Grade: 2
- Status: open
- Rule: docs/operations/gate-bypass.md, "What is green at once": while `gate.bypass` is true, a PR's gate is green at once, every stage is a PASS marked `bypass=D-151`, and the train's tier 2 is green without running a command.
- Evidence: PR #1024 (commit `9c41dc836`, the regime's default set to true, D-260) merged at 11:00 BRT under the bypass (`scripts/service status`, merged list). `scripts/test-suite` on `c5a21e700` (14:1x BRT): 141 script tests judged, 7 ran, 7 failed (7 files, 10 names, 43 failing assertions). First real measurement of the base, `scripts/gate-shadow run` on `3d641027` (14:05 BRT): exit 1 in the stage "script tests". The base was green again at `015512cf3` (14:2x BRT): passed, 45.3 s.
- Harm: the base was red for about three hours (10:52 to 14:2x BRT) while every PR gate and the train's tier 2 read green. Nothing showed BASE BROKEN to the lanes. #1024 and #1025 merged in that window; no gate ran the tests the regime broke, because the bypass ran none.
- Proposal: keep the bypass, because it is the regime's speed, but stop it from hiding a red base: (a) the train refuses a merge while the base's last real gate is red (the program's R1, D-206 (e)); (b) a PR whose diff touches shared tooling, the registry defaults or the regime runs its script tests for real even under the bypass.
- Impact: the train's throughput, which stops while the base is red until someone fixes it; the regime's 10 s goal, which gains a few tests per such PR. Reversible: both are code changes behind a flag; `gate.bypass` itself is not touched.
