# CENSO-NO-MANIFESTO plan: the census belongs to the unit, not to a shared file

## Why

Daniel, 17:17 (twice): why are units editing a file in the code, and would an API not settle these configuration
questions for good, at 1,000 PRs a day? N writers on one file make N(N-1)/2 pairs, and any pair can need a merge.
100 writers a day make 4,950 pairs; 1,000 make 499,500. Merging does not lower the collision rate. It only lowers how
many collisions reach a person. An append-only record per writer has no pairs.

## The brief's decisions (recorded before any code)

1. **The census becomes an append-only record per unit.** One command writes it and nobody edits it by hand. The
   per-area document stops being the source of truth (step 3, decided by Daniel, not reopened).
2. **The writer is a command.** It is shaped like `scripts/config`: `scripts/census add <path> --why <why>`,
   `remove`, `list`, `show <path>`. It takes the unit from the manifests, records actor, reason and date, and refuses a
   path that belongs to no unit or to two. A hand edit of the record fails a check, the same way an unregistered
   literal does.
3. **The per-area file is derived.** It is generated by a `scripts/generate` target with `committed: false` and read
   on demand, the same way as `context-map` and `docs`. No PR carries it, so no PR can conflict on it.
4. **The read stays hermetic.** The gate judges a commit from its checkout alone. The readers
   (`scripts/lib/structure.py`, `scripts/lib/literal_census.py`, `apps/web/scripts/lib/census-files.ts` and its
   callers) read the records in the tree and build the area view in memory.
5. **Other derived shared files get the same treatment (3bis).** If a file must stay committed, a regenerating merge
   driver settles its conflicts. If the generator can build it on demand, it stops being committed.
6. **Constraints.** Never lose an entry. No gate threshold is loosened. No production change (D-054). Merge commits
   only, and this PR is never merged by its author.

## Design

### The record (step 2): `units/<id>/census.jsonl`, schema `contracts/units/census.v1.json` (one event per line, C9)

```json
{"at": "2026-10-28", "by": "...", "census": "catalog", "digest": "<sha256>", "entry": {"domains": ["..."], "holds": "..."}, "n": 1, "op": "add", "path": "apps/web/src/app/vocabulary.ts", "prev": "0", "why": "..."}
```

- `census` is `catalog` (a D-063 literal catalog: `domains`, `holds`, optional `generatedFrom` and `builders`) or
  `baseline` (an absolute-census exception: `{"<kind> <value as JSON>": count}`).
- `op` is `add` (the path is new to this census of the unit), `set` (it replaces the live entry) or `remove`.
- `digest` is `census.digest_algorithm` of the event without its digest, and `prev` is the digest before it
  (`census.genesis_digest` for the first): `scripts/lib/audit_chain.py`.

The check (`scripts/census check`, run by `structure-check`) refuses:

- a file that does not match the schema, or a `unit` that differs from its folder or has no manifest
- a file whose text is not the writer's canonical rendering
- a broken digest chain
- a fold that adds an entry that is already live, or sets or removes one that is not
- a live entry whose path resolves to no unit, to two units, or to a different unit than the record's (`units.units_of`)
- against the base, a record whose events at the base are not a prefix of its events now (append-only)
- a committed per-area file once the door is closed (step 5)

### The writer (step 3b): `scripts/census`

| Command | What it does |
|---|---|
| `add <path> --why W [--actor A] --catalog --domain D… --holds H [--builder B…] [--generated-from S]` | Appends a catalog `add`, or a `set` with `--replace`. |
| `add <path> --why W [--actor A]` | Appends a baseline `add`, with the counts taken from the scan. |
| `remove <path> --why W [--catalog]` | Appends a `remove`. |
| `sync [--unit U] --why W` | Brings each baseline entry in scope up to date with the scan (`set`, `add`, `remove`). This replaces `pnpm literals:census --write`. |
| `migrate <area> --why W` | Moves an old per-area file's entries, from both censuses, into the records of their units, and deletes the file. |
| `list [--unit U] [--census catalog\|baseline] [--paths]` | Prints `unit	census	path` for each live entry, or only the paths. |
| `show <path>` | Prints the unit, the live entry and the history of the path. |
| `check [--base REF]` | Runs the door described above. |

The actor defaults to `git config user.email`, or `$USER` when that is unset. The date is the UTC date.

### The derived area view (step 3c): `scripts/generate census`

`committed: false`. It renders `scripts/lib/literal-catalogs/<area>.json` and
`scripts/lib/absolute-literals-baseline/<area>.json`, in their old shapes, from the records. It prints them, or writes
them under `--out`. The readers call the same functions in memory.

### No remote store (step 3d)

A census entry is an input to a verdict. If it lived in a remote store, the same commit could be judged differently
at two different times. `scripts/config` and `forge_events` already offer a remote store
(`config.store_adapter: file | github`), and the gate pins `file` for exactly this reason. Here the API is the write
path and the query path, not a network hop. The sentence also goes in `docs/architecture/UNITS.md`.

### 3bis: the same door for the other derived shared files

| File | Committed? | Why | Conflict handling |
|---|---|---|---|
| per-area census files | **no** | Nothing outside this repository reads them. The readers can build them in memory. | None needed: no PR carries them. |
| `CODEOWNERS` | **yes** | GitHub reads it from the tree when it assigns reviewers. An uncommitted file would break review assignment. | `.gitattributes`: `CODEOWNERS merge=regenerate`. |
| `apps/web/tsconfig.paths.json` | **yes** | `tsc`, Next, ESLint, vitest and every editor read it from the tree through `extends`. Building it on demand would need the generator to run before each of those entry points, and the build does not own most of them (an IDE opening the project, for one). | `.gitattributes`: `apps/web/tsconfig.paths.json merge=regenerate`. |

How the driver works (`scripts/merge-regenerate %O %A %B %P`): git merges in memory and calls the driver once per path
before it writes the worktree, so the merged tree is not on disk when the driver runs. The driver rebuilds that tree
itself:

1. It reads the other side from the `GITHEAD_<sha>` variable that `git merge` and `git pull` set.
2. It runs `git merge-tree --write-tree HEAD <theirs>`, with an inner flag set so the nested call does a plain 3-way
   merge.
3. It extracts that tree with `git archive` and runs `scripts/generate <target> --root <tree> --out <tmp>`, pinned to
   `OU_CONFIG_STORE=file`.
4. It writes the output as the merge result.

If the target's sources conflict, or no single other head is known (a rebase or a cherry-pick), the driver falls back
to `git merge-file`, and a real conflict stays a conflict. In every case, the `generated drift` stage still refuses a
stale result.

`bash scripts/cloud/setup.sh` registers the driver (`git config merge.regenerate.*`). Every agent session already runs
that script from SessionStart, and so do the Cursor and Codex setups.
