# db-migrations contract (1.0.0)

The unit is logical (S1, P-03): `apps/web/drizzle/**` keeps its paths. The manifest's `contract` is `{entry: meta/_journal.json, version: 1.0.0}`, so the bare address `@ou/db-migrations` names the journal and `@ou/db-migrations/<file>` any file of the unit (generated by `scripts/generate addresses`).

| Part | Shape other units rely on | Readers (not edited here) |
|---|---|---|
| `meta/_journal.json` | `entries[]` with `idx` (contiguous from 1), `tag` (`<NNNN>_<name>`), `when`, `breakpoints` | drizzle-kit (`drizzle.config.ts`), `test/fixtures/migrations.ts` (`MIGRATION_COUNT`), the migration integration tests, `scripts/lib/structure.py` (D-054) |
| `<tag>.sql` | one forward migration per journal entry, statements split by drizzle breakpoints | drizzle-kit, `scripts/lib/assets.py` (`migration:<name>` markers), integration tests |
| `meta/<NNNN>_snapshot.json` | one drizzle snapshot per entry | drizzle-kit, structure-check |

Rules:
- Forward only. A migration is never edited or renumbered once merged; the journal stays global and its next number is allocated by the train, never by hand (P-06).
- Only the db package speaks SQL; this unit owns the schema files and no runtime code.
- A change to the journal or snapshot format is breaking: it goes expand->contract (P-07, D-029) and bumps the major version. Adding a migration is not a contract change.

Literals: none (the no-literals check finds zero; no `x-literal-sites` entry names the unit; SQL identifiers are the schema itself). Battery: `scripts/unit-battery db-migrations` (contract step), limit `battery.unit_time_limit`. Generated outputs: `scripts/generate --check` shows no drift.
