**Under the gate bypass or an exception-regime lift of the gate lock, the `script tests` stage still runs, and a red selected test fails the gate; every other stage stays bypassed (amends D-151 and D-260; GR).** On 03/11 a selected script test failed at the PR head and `scripts/deliver` merged anyway, three times: `config-readers.test.sh` on #196 (red at 4153bc1d3 and at the merged head 5aa289cdd, green on the base), `generate-tree.test.sh` on #204 and #208 (base red, lane digest 1561 > 1536 bytes). The cause was not the test cache, the F73 base class or the known-defect step: the regime (D-260, lock `gate` lifted) answered `gate-local` with `gate_bypass.py run`, which wrote a PASS for every stage including `script tests`, so no test ran. Lanes then spent about 2,280 s debugging bases and heads the gate had called green. Now `gate_bypass.run` runs the tests the diff selects (the gate's own selector over base...head, the whole suite when the diff is unreadable) through the test cache on a checkout of the head, writes the stage with its true result (no `bypass` mark) and a failure to run them is a FAIL. The bypass also skips the known-defect and base-class excuses (KD1, F73): a selected test red on the base too is red, because the bypass leaves no review that would catch it; the other stages keep D-151 green-at-once, and tier 2 stays unbypassed (D-259). Revert path: revert this change (`gate_bypass.write_stages`/`run`, `scripts/tests/test_gate_bypass.py`); D-151 and D-260 then hold as written.
