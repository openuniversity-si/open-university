**The infra judge publishes tower/gate on the head, before the landing, so the forge can require it (F37-INFRA-CHECK; Daniel approved making tower/gate required, condition: prove it first on a real PR, then turn the rule on).** Finding of the previous lane (PR #381): with delivery.judge=infra only the box gate wrote tower/gate; gate_infra.land never did. 1. gate_status.check_hooks (the gate's own publisher, gate_status.Publisher, which forge-events.check_run_publisher routes to the control plane) posts pending on the head before the checks are created and success or failure from the verdict BEFORE the landing job exists: with before_landing set, judge creates the landing only after the checks are decided, because a required check must be green on the head for the forge to merge. Red or late posts failure and creates no landing. 2. It is gated by gate.check_run_enabled and forge-events.status_enabled, and fail-open: a failed publish is logged on stderr and the delivery goes on while the forge does not require the check. gate.check_run_required (default false) turns that into a block: with it on, a failed pending or success publish raises and nothing merges (a failed failure publish never changes a red verdict). It is set true in the registry in the same step that the ruleset is created. 3. Defaults changed to make this the normal path: gate.check_run_enabled true and forge-events.check_run_publisher control (client is refused by Origin unless the credential is an oit_ token, D-299). The box gate therefore also posts tower/gate through the control plane in every checkout, and a session without the events token logs the failure and goes on (fail-open) instead of failing. 4. The ruleset requiring tower/gate on mod/roadmap-integration is created only after a docs-only PR delivered through this path shows tower/gate on its head with the right conclusion in origin pr checks. Revert: origin ruleset delete <id> (the rule), gate.check_run_enabled false (the publisher), or revert the PR that carries this record.
