**The runner's production path has no AI session: a systemd user service that restarts by itself, a liveness watch for the hung process, and the install steps.** The train died on 01/11 with the session that ran it; the design is that no session is needed. `scripts/service runner --print-unit [NAME] [--kind K]` prints three units from `services/runner/*.tmpl` (data, not code): `tower-runner.service` (Wants/After network-online, `Restart=always`, `RestartSec=10`, `StartLimitIntervalSec=0` so a crash loop is never abandoned, the checkout's `.toolchain/bin` on PATH, an optional `EnvironmentFile=-%h/.config/the-tower/runner.env` that only systemd reads), and a watch (`tower-runner-watch.service` and `.timer`, every 5 min) that runs `scripts/service liveness` and restarts the runner when it fails. `Restart=` sees a crash, not a hang; the runner's heartbeat thread beats while a job runs, so a stale heartbeat (`service.heartbeat_stale_s`, 180 s) is a dead or hung process, not a long gate. `scripts/service liveness` exits 0 when this machine's runner beat in time and 1 with the reason otherwise (the probe, also usable by any monitor). `docs/operations/services.md` has the install and the five checks (status, liveness, crash, hang, reboot). Not done here, and stated: nothing was installed or run on the e2-micro (D-155: no loop, no session on the VM); the container tests cover the unit text, the probe's three answers (no state, fresh, stale) and the refusal of an unknown unit name. The VM install is the first use of the steps.
