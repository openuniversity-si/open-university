**The gate's verdict is an Origin check run, tower/gate on the judged head, posted by the control plane, which alone holds the Origin app's signing key; a ruleset of the base branch will require it (VAZÃO F37; gate change under D-292).** Origin refuses a check run from a user principal (403 "This Origin endpoint does not support user principals"; scope repository:checks:write is integration-only), so the gate's own credential can never post it, and the PRs carry no check at all: the forge does not ask for the gate's proof. Three rules follow:
1. The check run is its own switch, gate.check_run_enabled (default false), apart from the comment panel gate.status_enabled: on, the gate writes tower/gate pending at begin and success or failure from the verdict on the exact head it judged, with no comment, no gate.started and no verdict hooks.
2. The engine never holds the app key. forge-events.check_run_publisher (client or control, default client) chooses who posts: control sends the Origin check-run body to the control plane (POST /v1/check-run, the events token), and the Worker mints an app JWT (EdDSA over Ed25519, iss the app id, aud origin-apps, 300 s, as the origin CLI signs it), exchanges it for an oit_ installation token (POST /v1/origin/app/installations/{id}/access_tokens) and posts the run for its own REPO only. Without ORIGIN_APP_PRIVATE_KEY, ORIGIN_APP_ID and ORIGIN_APP_INSTALLATION_ID the route answers 503 not configured.
3. Nothing changes until the Torre sets those three on the Worker, deploys it and turns both keys on; then a ruleset of mod/roadmap-integration requires the check of suite tower of the app, and a PR head without a green tower/gate is not mergeable by the forge.
Revert: set gate.check_run_enabled false (the check stops), or revert the PR that carries this record.
