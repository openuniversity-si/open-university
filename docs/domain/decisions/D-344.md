**A pull request from a fork that changes the gate workflow is an accepted residual of THREAT-gate until 2026-12-19, under a rule for sessions, while a push rule on .github/workflows is checked (D-335, D-337; decided by the session under D-325; Daniel may supersede it).** The independent re-review of 19/11 (D-333) found that a pull request from a fork brings its own .github/workflows/tower-gate.yml into the pull request run and the merge-group run, so a check the ruleset requires, bound to the GitHub Actions app, can be made green by that changed workflow. No barrier inside the repository can refuse it: every check of the tree runs inside the workflow the change can replace. What stands between such a change and main is that a pull request reaches the merge queue only by a writer queueing it (auto-merge or the queue button): the writers are the owner and the sessions acting for him, and a branch of the repository cannot carry a workflow change at all without the workflow scope (D-087). The rule this decision adds: a session never queues, nor turns auto-merge on for, a pull request from a fork whose diff touches .github/; the owner reads such a diff before queueing it. The residual is accepted until 2026-12-19, owner administration, through two exemptions: TAIL-gate-fork-workflow for THREAT-gate and TAIL-ssdf-pw2-gate for CTRL-ssdf-pw.2, which is partial only because THREAT-gate is not reviewed (ten of the eleven threat models are). It ends earlier when a repository-side barrier exists: a push rule that refuses a change to .github/workflows/** on main except by the owner, which the Torre is checking for this plan. Revert path: delete the two exemption files, or let them lapse.
