**The port and the webhook ingress write to the database directly, from a Lambda in the VPC, with no SQS queue in phase 1 (amends the ingress row of ARQUITETURA-ALVO §2; the session's judgment, D-294, carrying out Daniel's request of 04/11 13:27 BRT to implement the plan).** ARQUITETURA-ALVO §2 put API Gateway, a Lambda that checks the signature and an SQS queue in front of the service. Under the A1's network (D-303: no NAT, ~US$ 32 a month per zone, and no interface endpoints, ~US$ 7 a month each), a Lambda reaches either SQS, outside the VPC, or the private database, inside it, never both, and the queries of the port (§5: a job, the log with the filters and groups the caller defines) need the database. So the port is one Lambda in the private subnets, with the tasks' security group and IAM authentication to RDS, behind the HTTP API of API Gateway: each command is one statement that writes its rows and its event together, each query reads only the caller's rows, and the database is already the queue (DBOS keeps its queues in it). At 1 PR/min (~0.1 request/s) and at 1 PR/s (~5 requests/s) one transaction per command costs less than a queue and its consumer, and the reserved concurrency of the Lambda bounds the connections. SQS comes back, between API Gateway and the service, when a measured burst refuses commands for lack of connections. Proof: scripts/tests/test_infra_port.py runs the acceptance test through the port with two tenants on the toolchain's PostgreSQL. Revert path: revert this record and put SQS back between API Gateway and the service.
