A verdict is about the tree the stages ran in, and the PR head read at the start of the run is not a promise that the head is still current when the record is written. Incident (PR #1023): the lap pushed 9adbee57; the gate read GitHub's stale head 9c41dc83 and wrote 9c41dc83.dev.pass; the train merged 9c41dc83, whose tree fails regime.test.sh and train.test.sh. Three levels. Design: the record is keyed by the head the run read, and nothing ties it to the tree the stages ran in or checks that the head is still the PR's when the record is written. Class: a reader's answer (the REST head, a cached or stale read) is trusted as the verdict's identity. Case: 9c41dc83, merged. Checked here: the verdict API (scripts/lib/gate_verdict.py) refuses a moved head (test_gate_verdict.py: a moved PR head is UNOBSERVABLE), so the gap is the writer of dev.pass in scripts/gate-local (writes under the sha read at the start, line ~404) and the train, which merges on that record. Not reproduced here: the incident's report folder is in lane 1's container, and which path ran the tests (a worktree at 9c41dc83, or a result reused by key) is not yet confirmed. Redesign: a record is written only when the head the PR reports is still the tested head at that moment, and the train merges only on a record whose sha is that head. Alternatives: (A) retry the read: narrows the window, does not close it. (B) the writer re-reads the head and checks the tree's HEAD equals the recorded sha before writing: closes it at the writer. (C) the train re-checks the PR head before the merge and refuses a record that is not its head: closes the merge door regardless of the writer. Choice: B and C together, in gate-local (engine-gate-run) and the train (engine-train), not in this unit; this unit's API already behaves as B needs.
