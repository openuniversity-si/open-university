# Audit and plan before commits (Daniel, Oct 26 23:26)

Every session runs two phases before its first code commit:
1. AUDIT (read-only; parallel read sub-agents allowed): read the brief, the PR/branch state, the files in scope and their tests (scripts/lib/gate-script-tests.json covers), the known-defects list, and what already exists that the brief may duplicate. Do NOT run full suites here; only cheap evidence.
2. PLAN: write the plan as the PR DESCRIPTION, section "## Plan" (order: at launch, BEFORE the audit, create your branch and open the PR as a DRAFT whose description is the brief summary. The audit and the plan are FILES in the repo with their own commits: commit 1 = docs/units/<unit>/audit.md (findings and evidence), commit 2 = docs/units/<unit>/plan.md (the Plan below). The PR description mirrors plan.md. Only then code commits. If the plan changes, commit the new plan.md and update the description; an existing PR adds these files the same way). It contains: (a) the commits as a dependency graph, each with the files it owns (no file owned by two parallel commits) and which run in parallel; (b) premises, each with its blast radius; mark any premise whose failure would change scope, spend money, touch production or the source of truth as CRITICAL; (c) the targeted tests per commit and the single final gate; (d) known base defects expected and their owners.
Then execute at once (decide, then report): parallel commits via sub-agents per the graph, small pushed commits. A CRITICAL premise you cannot verify cheaply: pick the safest reversible option, act, and flag it in the Plan. If the plan changes, edit the PR description and say so in one comment.
