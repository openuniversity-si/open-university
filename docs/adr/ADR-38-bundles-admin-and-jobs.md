# ADR-38 — Course bundles, admin scope and durable jobs

Status: deprecated by D-111 (the Open University product left this repository; PADRAO-DEV F3a).

Status: accepted for the structural audit (states 4.3 and 4.4).

A course bundle is validated, then applied in one unit of work. YouTube metadata is resolved before that transaction.
`catalog_jobs` records a ship attempt. The lease token fences a worker that resumes after a crash. A lease lasts 60 s. `ship` claims a bundle when a worker starts it, renews the lease in its last third (`POST /jobs/:id/renew`) before each checkpoint, and claims again a lease that lapsed while a batch waited for its one release: the job resumes at its stage with a new token, or stops if another ship holds it.
Claim, advance and complete require the actor, the environment and a live lease. A hash mismatch does not update the row.
When an admin identity is present, permissions are deny-by-default. The admin key a deployment accepts is that deployment's operator key: its environment comes from `VERCEL_ENV` (`production` is `prod`, anything else `preview`), never from the request body, so a production deployment claims prod jobs, refuses preview claims and rejects a preview reset. Separate preview and prod keys are separate values of `TOWER_ADMIN_MEDIA_SECRET` per Vercel environment; the CLI holds them as `TOWER_ADMIN_SECRET_PROD` and `TOWER_ADMIN_SECRET_PREVIEW` and sends each request only its target's key. Draft preparation is not a publish privilege.
The ship command talks only to the admin HTTP API.

`tower-catalog ship` applies the bundle as a draft, then moves that draft to review and publishes it. One course builds one release (`POST /courses/:id/publish`). `--batch` builds one release for the whole batch (`POST /courses/publish-batch`). A second ship of the same bundle finds the verified job and does not upload, apply, or publish again. A job left before `VERIFIED` after its course was published (the process stopped past the batch release) is reconciled: when the active release already shows the bundle (course fields, editions, lessons, approved texts), ship records that release on the job, verifies and completes it, and never publishes again; any difference takes the normal path. `POST /jobs/claim` is not HTTP-idempotent: the job row is the idempotency record, and replaying the first `acquired` response would hide a later `VERIFIED` stage.

CourseBundleV1 may carry `languageLabel`, `areaId`, `subareaId`, `licenseCode`, `sourceId`, `attributionText`, `canonicalUrl`, `rightsStatus` and `coverProvisional`. Each is optional. A subarea requires its area. `coverProvisional: true` requires a subarea and sets `courses.cover_provisional`, so a course without its own poster, heroes or OG inherits the subarea's shared covers (ADR-30); an absent flag leaves the stored value. Apply locks the course and subarea media owners, as `PATCH /courses/:id` does, and refuses a change that leaves a published course without an active required cover. Unknown license, source, area or subarea values fail when the bundle is applied. Covers are optional relative paths. Ship uploads missing bytes through the admin media API and stores them at `m/<sha256>.<ext>`, then attaches them to the course. The command prints `validate`, `upload`, `apply`, `publish`, `release`, `verify` and the total.
