# ADR-29 — Disposable PR databases and verified delivery

Status: deprecated by D-111 (the Open University product left this repository; PADRAO-DEV F3a).

Accepted 2026-10-18. Daniel authorized the small Neon compute/storage cost **only for numbered `pr-<n>` branches** at 01:17 BRT. No plan changes or other paid resources are authorized. Vercel stays on Hobby. No GitHub Actions or application feature flags.

## Decision

`scripts/gate-local --pr <n>` checks out the exact head, runs the entire ADR-28 gate, and concurrently provisions/migrates a Neon child of production. After the production build, the same build starts locally against that disposable database: `/api/health` must read the database, and the admin API doctor must have no errors. Migrations use the existing migration runner with explicit target `pr`; no SQL catalog operations, seed, catalog import or publish runs on the clone. Only the full successful gate writes the head's pass plus `pr=<n>` / `neon=pr-<n>`. `merge-phase` requires this proof for main.

The existing external `load_neon_db_env` remains for permanent environments. PR operations resolve their direct URI via the same Neon connection_uri API and inject `APP_DATABASE_URL_PR_UNPOOLED` only into child processes. An operations-only pg preload lets the local Next acceptance server use WebSockets because this box blocks TCP 5432; application/production database code stays portable PostgreSQL.

Before creating a branch, `neon-pr` prunes numbered PR children that are closed/merged or older than **24 hours** (even if still open). The current PR is retained for repeat gates. Protected/default branches, non-PR names and branches with children are never deleted. The parent must be the configured production branch. GitHub/API uncertainty stops the operation. Concurrent local lifecycle commands share a lock. `neon-pr close <n>` closes the PR and deletes its database; `merge-phase` deletes after merge. If someone closes through GitHub, run `neon-pr prune`; the next provision also cleans it. No background scheduler or Actions dependency.

At most **3** disposable branches may coexist: creation at 3 is refused, and any state with **more than 3** is refused explicitly. Creation is also refused at **10 total branches**, regardless of plan. Permanent branches observed: **3** (`main`, `v1-preview`, `v1-staging`). With 3 PR branches the total is 6/10. Compute is fixed at **0.25 CU** (minimum and maximum); autosuspend is **300 seconds**, the Launch plan minimum. The API schema permits 60 s globally, but this project rejects 60 s with HTTP 412 (`suspend interval is too short for your plan`); 60 s requires a different plan, which is not authorized. Existing PR computes outside this envelope are refused rather than resized silently.

`scripts/ship-verify <n>` serializes releases and invokes only `merge-phase` to merge. Its production contract is now defined by [ADR-32](ADR-32-hard-production-verification.md): the expected commit must be READY and serve healthy pages and direct-origin covers. HTML/pixel comparisons are optional evidence and never trigger rollback. The previous parity-driven policy below is retained as incident history, superseded by ADR-32.

Only a confirmed hard production failure may promote the captured previous deployment, after the same read-only hard check on its deployment URL and an ancestry guard at commit `15090790`. Unknown observer state never authorizes a promotion. Production doctor is outside this path; the gate's disposable-database doctor remains required. Per-step and total timings, production results and failure/rollback reports remain in `impl/v-evidence/`; Neon cleanup remains in place. Delivery progress is the merge commit and the verified production deploy, not a progress file. No GitHub Actions dependency.

## Limits and cost evidence

Authenticated read-only API inspection on 2026-10-18 confirmed organization `plan=launch` and project owner `subscription_type=launch_v3`; it is **not Free**. Launch includes 10 branches. Free has a hard limit of 10 (no extra branches); Launch extras cost $1.50/branch-month, prorated hourly. The local 10-total guard avoids those extras. Free includes 100 CU-h/project/month and 1 GB/project (20 GB/account); Launch compute is $0.106/CU-h and storage $0.35/GB-month. A 0.25-CU PR compute costs $0.0265/hour of active time, approximately **$0.000442/minute**, including idle time before suspension. Child branches initially share data; their writes accumulate a storage delta (capped at logical size). Deleting the branch removes its compute and future branch storage use; already accrued usage remains billable. No project plan/production compute settings are modified.

## Historical follow-up: the Home parity incident and root cause (superseded by ADR-32)

PR #161 merged as `20183c7`, then the verifier safely promoted `6eae557` after Home parity failed. The only normalized server-markup difference was `aria-current="page"` on Home. Investigation confirmed **no src, Next config or dependency changes** between commits. Vercel CLI build logs show Next 16.4.0 and identical database release 123 (`0576256da0fc`) in both builds; production env names/timestamps were unchanged. No environment or catalog updates were performed by V.

The old deployment's ISR response was `x-vercel-cache: STALE` with RSC canonical segments `["","index"]`; the new prerender had `["",""]`. Consequently `usePathname` seeded the old router with `/index` and `topNavContext` chose no active tab, even though the browser URL was `/`. Waiting for hydration alone did **not** fix it: the old DOM remained muted with underline opacity 0. This is a real difference between those initial cached states, and must not be removed by stripping accessibility attributes.

In the **same old deployment**, real Universities → Home client navigation produces `aria-current=page`, white text and underline opacity 1. The new deployment produces exactly the same normalized DOM after the same navigation. Thus #161 did not introduce a new component/design behavior: the original capture compared different router states seeded by ISR versus prerender. Evidence including raw HTML, hydrated DOM, route/cache metadata and screenshots is in `impl/v-evidence/root-cause/`. No product source or visual rule is changed to work around the cache artifact.

The capture now retains initial server HTML **and** landing DOM, waits for AuthProvider's signed-out session effect (hydration) and two animation frames, then uses actual Next Links Universities → Home before taking the Home comparison snapshot. Other pages are captured after the same hydration/session readiness. It never assigns DOM attributes or mutates router internals, and the normalizer still preserves `aria-current`, CSS classes, inline styles, images and text. Initial-server differences remain in a separate report; canonical-client-state parity is the gate. This proves parity in the defined route state, not byte identity of ISR versus prerender responses or every initial paint.

A local browser regression reproduces stale `/index` and fresh `/` seeds plus delayed hydration: real link navigation must converge, while actual aria/style changes must still produce different normalized snapshots. A blocked/missing session or failed navigation fails capture instead of accepting an unfinished page. Rollback parity uses its own filename, preserving the failed attempt's report. Stage timing messages explicitly say completion rather than implying success. The follow-up also adopts Daniel's 90-second gate tolerance with boundary tests, retaining every check and the separate 60-second content-delivery goal.

The #162 retry exposed two additional capture races, with production again promoted back to G: Chromium returned the old health response while a separate request saw the new commit, and asynchronous Next/Image `onError` changed `style="color:transparent"` to an empty style during the lesson snapshot. Health now uses a unique cache key per request (and `no-cache` in the polling client), checks the expected commit before capture and unchanged health afterward. Markup capture pauses image downloads before requesting any page, preventing asynchronous image load/error mutations; it keeps every image URL, dimension, alt text and authored style and does not substitute image bytes. This is HTML parity, not an image availability or pixel check. DOM readiness uses DOMContentLoaded and the hydrated route/session effect, not the load event that depends on paused images. A broken-image fixture and unique-health-key regressions cover both cases. Two repeated corrected captures on restored G produced 4/4 identical snapshots; the normalizer still rejects genuine aria/style changes.
