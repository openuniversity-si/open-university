# ADR-32 — Hard production verification and guarded rollback

Status: deprecated by D-111 (the Open University product left this repository; PADRAO-DEV F3a).

Accepted 2026-10-19. Supersedes ADR-29's production parity and automatic-action policy. The delivery audit found six false rollbacks and no true positive; several restored the paid optimizer's image 402 failure.

## Decision

`scripts/ship-verify <PR>` asks whether production is up at the merge commit. It reuses `production_check.verify`: the project's production deployment must be READY with the expected commit and assigned production alias; uncached `/api/health` must identify that commit and database catalog; Home, universities, a linked course and a linked lesson must return 200 HTML with essential markers and real covers; Home and course must contain course/lesson links. Every distinct rendered cover must return 200, image MIME and nonempty bytes from `media.openuniversity.si`. The paid optimizer and unexpected image origins are failures. Health and deployment identity are checked again after the smoke.

The successful path has no browser capture and no production doctor. The local gate still requires the disposable-database doctor. Production doctor can be run separately for catalog maintenance; its latency or observer failures cannot decide code rollback.

Deployment readiness has a 120-second monotonic budget. Failed ERROR/CANCELED deployments are also found when the alias still serves the old READY deployment. HTTP/health/markup/image checks retry up to three times within a further 30-second budget, ten seconds apart (an in-flight request is bounded at 12 seconds). The readiness and smoke budgets do not impose a delay on success. Old ISR markup is not compared against another deployment; temporarily incomplete markup is retried. Unique health nonces work even when the wall clock stops or repeats. Production's existing explicit link-preview user agent avoids the known WAF bot challenge; no WAF or environment configuration changes are made. Authentication/WAF/rate-limit responses (401/403/429) and Vercel control-plane errors are inconclusive, never rollback authorization. Redirects are not followed, and credentials never reach page/image origins.

Each network operation and retry sleep is observed with monotonic and wall clocks. A gap over 45 seconds or wall/monotonic discrepancy over ten seconds invalidates either success or failure, resets the retry budget and requires a fresh observation. Three repeated gaps stop inconclusively rather than loop forever. Normal deadlines never use wall time. A VM that freezes every available clock cannot be detected by local clocks alone; independent retries and a fresh production recheck before promotion still prevent acting on a single failed observation.

## Rollback

Only a confirmed merge plus a hard production `CheckError` can authorize rollback: unreachable/5xx, deployment/health identity failure after waiting, failed deployment, missing essential/content links/covers, or broken cover responses. Merge-client ambiguity is resolved from GitHub's read-only PR state; a confirmed merge continues verification, an unconfirmed merge stops without promotion. Cleanup, signals, capture failures and unexpected tooling errors do not authorize rollback.

Before promotion, the previous full commit must be provably descended from `1509079089d65cc4a607164e660daa3c2cb5d54d` (inclusive) using `git merge-base --is-ancestor`. Missing git objects or ancestry uncertainty refuse rollback. The same hard checker runs against the previous immutable deployment URL, validating project, production target, READY state, commit, health, four pages and every cover. Only its current production alias assignment is omitted. A protected, unreachable or unhealthy candidate is refused with a loud warning and nonzero delivery exit plus `failure.json`. A broken baseline does not prevent shipping its fix.

Production is checked afresh after candidate validation. Recovery cancels promotion; inconclusive rechecks refuse it. Read-only GitHub main identity is checked before candidate validation and again immediately before promotion to avoid replacing a concurrent delivery. `vercel promote <previous-url> --yes` reassigns production without another build, followed by the full hard check on the public alias and exact previous deployment ID. This is simpler and faster than an automatic revert PR/build and does not write catalog data or modify environment settings. It does **not** revert main, migrations or catalog content: `failure.json` explicitly identifies the failed check/URL/status, rollback commit and unchanged main. After a real rollback the orchestrator must reconcile main through a reviewed fix/revert PR before the next delivery.

## Evidence and validation

`--direct-images` remains compatible, adding optional HTML and visual reports. HTML differences (including aria-current and preconnect), JPEG noise, catalog differences and browser failures remain evidence only. The HTML observer uses a fresh page per URL with health checks around each page; the visual observer resets the document between routes and disables GPU, incorporating the relevant resume-166 capture fixes. No normalization of meaningful differences is added to make production pass. The default path does not depend on Chromium or a local browser's lifecycle.

The existing single-delivery flock, merge preflight and post-merge numbered Neon cleanup remain. Delivery progress is the merge commit and the verified production deploy, not a progress file. `timings.json` records every executed step, merge-to-verified time and total, and the total is printed even on failure. `production.json`, `success.json`, candidate verification and `failure.json` retain the decision evidence without tokens or API payload dumps. Optional comparison failures have their own warning files.

Offline injected-failure tests run the real checker through fake HTTP, Vercel and GitHub. Old assertions that parity/doctor/ambiguous merge must promote are replaced by assertions that these never promote; hard failures still require healthy-candidate verification, actual fake promotion and verification of the restored public deployment. No test is skipped or deleted. The audit's three real deliveries and merge-to-verified p50 under three minutes must be measured by the orchestrator after merge; offline timings are not production performance evidence.
