# F1.2 — authoring per commit down (target 300–400 counted commits/day)

Phase 1, second sub-phase (RC-002: serial, approved by Daniel 31/10 15:23 BRT). F1.1 removed the lane's idle wait
(pipelined lane, D-142; stale gates dropped, D-141/D-145); what is left in the lane is authoring.

## Auditoria
Why does a commit take as long as it does? In this session's F1.1 the push of a new script (`scripts/flow-metrics`, its
test, its unit) was refused five times in a row before it landed: the literal census, the missing unit manifest, the
missing asset entry, the missing covers manifest, the CODEOWNERS regeneration. Each refusal is a correct rule, and each
costs a round trip of reading the error, editing one file and pushing again. The rules are fine; what is missing is
the one place that knows the whole set. A request that has happened before and will plainly happen again (add a script,
a test, a unit path) is a capability (STRUCTURE A4), not five edits. So why is authoring per commit high? Part of it is
rework against checks the author could have been told about once, before writing.

## Plano
1. **Redesign: `scripts/scaffold script <name> --unit <unit>`**: one command that creates the wrapper, the library module,
   the test and its wrapper, the covers manifest, the unit's paths, the asset entry and the regenerated CODEOWNERS, so a new
   script starts structure-clean and the author writes only the logic.
2. **Class**: `scripts/flow-metrics --admit` (F1.1, D-144) runs before the push so empty, fixup and split commits never
   cost a gate; the runbook names both commands.
3. **Point**: measure authoring per commit per day (`flow-metrics --cycles`) and the refusals per new script before and
   after.

## Medição

(31/10 19:08 BRT, F1.1 closed): 14.7 an hour over the last three hours, 8.4 over twelve; this session's own authoring gap is
2.0 minutes a commit (46 commits since 15:00 BRT, p25 0.9, p75 5.3), so a lane is bounded by its PR cadence, not by its typing.
Authoring per commit (`--cycles`, `authoring_s`) and the refusals per new script (before the scaffold: five in a row) are the

### Did the goal improve or only the number?
**Number:** 18.0 counted commits an hour over the last three hours (17, 27, 10; 12.5 was needed for 300 a day), 177 in the last 24 hours. Authoring per commit on the landing day fell from 385 s (the earlier reading) to 136 s (`--cycles`); this session's median gap between commits is 2.5 minutes over the last three hours. Guards: split 2.5 % (was 2.6), tangled 9.4 % (9.5), docs-only 36.6 % against 36.5 %: above its start value by about two commits in the whole history, which is what keeps the phase open.

**Goal:** yes, for what F1.2 aimed at. The lap that used to cost eight hand steps is one command (`lane-ship`, 32 to 60 s, D-158), it refuses what used to be learnt after the gate (a draft, an unticked plan item, a commit the rule would not count; D-159, D-162), a new script starts structure-clean (`scaffold`, D-146), and the base is watched by the real gate while the lane runs (D-157, D-163), which is what caught the two breaks of the day (D-153, D-154) and the channel limit (D-160). No part of this depends on the bypass, so unlike F1.1 the gain is the flow's. What remains outside it: the merge in about a minute still exists because the regime of exception gives the gate as green (D-151); the real gate on the e2-micro is lane 2's (D-155).
