# gate-speed — F11: uncached ≤ 10 s

Phase 11 of the [solução](../solucao.md) (D-133: two main targets; the work is `uncached_wall_s`, about 96 s and
about 320 CPU-s with no store at all). Every step of this phase is a green PR; the phase ends only at 10x measured on
`uncached_wall_s` (D-132), `cold_wall_s` kept ≤ 1 s, coverage ≥ 89.69 %, no failure.

## Auditoria
Why does the uncached suite do this work at all?
1. **Every test builds its world from nothing through real processes.** About 45,000 git processes a cold run:
   init, add, commit, fetch, push, rev-parse per test case. The train's family alone (its 16 files) spends about 59
   CPU-s, 27 in Python and 32 in about 6,800 processes (`rev-parse` 1,500, `update-ref` 800, `merge-tree` and
   `commit-tree` 330, `show`, `diff`, `add`, `commit`). The system that fails: the engine reaches git through raw
   subprocess calls (58 modules call git directly), so a test cannot hand it a world in memory; the train is the
   furthest along (a workspace object), and even it calls git by hand in five places.
2. **Each test case builds again the world another case already built** (the same seed, origin and checkout per
   setUp). The system that fails: a fixture is a procedure, not a value that can be built once and copied.

## Plano
Redesign first (D-132), from the most structural to the most superficial:
1. **Redesign (N8 → N6):** the engine reaches git through one port with two adapters, the git one and an in-memory
   one (objects, refs, trees as values; `merge-tree`'s three-way merge where the train asks for it); the tests whose
   subject is not git run on the in-memory adapter; the tests whose subject is git keep real repositories. The train
   and the gate first (the largest families), then every module that calls git.
2. **Class problems inside it (N7):** a test world is a value built once per run and copied per case.
3. **Point issues left:** whatever the measurement names after 1 and 2.

| Root | Alternative | Level | Choice |
|---|---|---|---|
| 1 | A1: batch the remaining git calls | remendo | no: linear |
| 1 | A2: memoize more answers | corrige a classe | no: 5–10 % (F5) |
| 1 | A3: one git port with an in-memory adapter, the train's workspace first | redesenho | **yes** |
| 2 | A1: worlds built once per run and copied | corrige a classe | **yes**, inside A3 |

Steps (green PRs): (1) this audit and the train's port completed: its five raw git calls become port methods
(`paths`, `has_path`, `files`, `count`, `is_ancestor`); (2) the in-memory adapter and the train fixture on it; (3) the
gate's family; (4) the remaining modules; each measured in ABBA order with repetitions.
