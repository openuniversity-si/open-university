# gate-speed — F4: ≤ 60 s

Phase 4 of the [solução](../solucao.md), opened by D-122 (Daniel, 31/10 03:08 BRT: the program goes on to about 10 s;
next, a fork server for the tests). F3 left the suite at 95.8 s cold on 4 vCPUs and 319.9 CPU-s ([F3](F3.md)).

## Auditoria
Measured on `dcb715b4` in a clean worktree of the session container: one cold run with every harness process logging
its own CPU at exit (start-up, harness, total, its children), and one cold run under `strace -f -e trace=execve`.
1. **What a cold run starts.** About 63,500 processes (the probe loop below excluded): git 54,315 (85 %: `rev-parse`
   9,187, `show` 5,379, `add` 4,511, `commit` 3,535, `init` 3,115, `fetch` 2,462, `ls-files` 2,457, …), `sh` 1,613,
   `bash` 1,175, git's transport helpers 1,521, Python 896 (642 scripts, 192 `-c`, 60 from stdin, 6 `-m`), `node` and
   `psql` 277 each. Git is the largest share of processes and of the system time (125 of the run's 369 CPU-s are
   kernel time); it is F5's and F6's subject.
2. **Every Python process starts from zero.** 824 processes ran under the hermetic harness. The interpreter's
   start-up plus the harness (its standard-library imports: `pathlib`, `re`, `enum`, `subprocess`, `argparse`,
   `urllib.parse`, …) cost 41.4 CPU-s of their 171.3, about 50 ms each, before the first line of the program. A
   prototype forked from an interpreter that had imported the standard library once runs the same harness and
   program for 17–20 ms of CPU where a fresh process pays 56–61 ms (`gate_classify.py`), and 50 ms where a fresh
   process pays 105 ms (`config.py get`, 171 runs a cold run): 35–55 ms saved per process, about 40–50 CPU-s a cold
   run (12–15 %). The system that fails: the test-execution system has no warm start; the ideal system (avaliação,
   item 3) pays start-up and imports once and forks per process.
3. **The 159 test files' own work** is 122 CPU-s, spread (the largest, `test_config_api.py`, 8.9 CPU-s); a fork
   server does not change it, the in-process restructuring of F6 does.
4. **A probe busy-waits.** `test_gate_test_cache_env.py`'s B8 and gate-gc probes spin `ps -o stat=` (and `grep`) in a
   loop with no pause while the runner they hold is stopped (its test file costs about 6 CPU-s a run); under tracing
   it never ended (11,545 rounds before it was stopped). It holds a race open on purpose; F6 replaces the spin with a wait on
   the event, the assertion unchanged.

## Plano
| Root | Alternative | Level | Choice |
|---|---|---|---|
| 2 | A1: trim the harness's imports (lazy `argparse`, `urllib.parse`, …) | remendo | no: a few ms, and the next import pays again |
| 2 | A2: call the engine in process where its CLI is not the subject (as F2 did for the structure check) | corrige a classe | no: per test, and a bash script that starts `python3` cannot |
| 2 | A3: a fork server. One interpreter per run imports the standard library, freezes its heap and listens on a private UNIX socket; a native client named `python3`, first on the tests' `PATH`, hands it argv, environment, working directory, umask, signal state and every open descriptor (SCM_RIGHTS); the fork rebuilds a fresh interpreter's state in a fresh interpreter's order (`sys.argv`, `sitecustomize` — the harness —, then `sys.path[0]`, then `__main__`), and the client exits with the child's exit status or signal, forwarding the signals it receives. Whatever it does not model (another uid, an interpreter flag, a `PYTHON*` variable, a terminal, a resource limit) execs the real interpreter. | redesenho | **yes** (D-122) |
| 4 | busy wait replaced by a wait on the event | corrige a classe | F6 |

The coverage guard measures the fork server too: under `COVERAGE_PROCESS_START` the server measures itself and each
fork restarts coverage with its own data file, so the lines the forks run are counted as a fresh process's are.

Commits: (1) D-122, the re-planned solução and this audit and plan; (2) the fork server and the fork's start, with
its tests; (3) the native client, built per run where a C compiler exists, the Python client elsewhere; (4) the
suite runs its tests under one fork server per run and reaps it before the CPU is read; (5) the measurement. Tests:
`scripts/tests/test_fork_server.py` (process contract: argv, environment, cwd, umask, descriptors, stdin, exit codes,
uncaught exceptions, signals, fallbacks, coverage), the changed suite tests, and the whole suite through
`scripts/test-suite --metrics`.
