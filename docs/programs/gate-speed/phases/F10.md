# gate-speed — F10: ≤ 10 s

Phase 10 of the [solução](../solucao.md), the first of the redesign at 10x a phase (D-129, Daniel 31/10 09:41: each
phase delivers 10x on the main metric; only a measured physical limit stops the program). F9 left the suite at about
96 s cold in the container.

As a cut of the unlock graph (D-132, [solução](../solucao.md)): F10 is node N1 alone, the smallest closed set that
delivered at least 10x (139x measured); it unlocks N2 (the gate and the runner) and N4 (keys per test file).

## Auditoria
1. **A fresh box judges again what every box has already judged.** A script test's key (`gate_test_cache.key`) is a
   digest of everything it reads: its covers' contents, the pinned toolchain and the gate's key parts; it names no
   box. Yet a PASS is kept only in the box that ran it (D-093: content keys per box), so every fresh container, every
   session and the e2-micro runner start from an empty store and run the whole suite: 95–99 s and 317–346 CPU-s here,
   past the e2-micro's stage limits there (D-119). The 2,371 test functions do not change between those runs; their
   inputs do not either. The system that fails: the result cache, the one part of the test-management system that
   already knows which inputs were judged, is not shared, so the suite's cold model is "run everything".

## Plano
| Root | Alternative | Level | Choice |
|---|---|---|---|
| 1 | A1: keep the local store of a box between sessions | remendo | no: a fresh box, the runner and every session still start empty |
| 1 | A2: the PASS records shared by their input key: one log ref on the forge (`gate.shared_results_ref`, moved forward only over git like the train's wake ref, a machine ref the pre-push hook lets through) whose tip holds every PASS of the last `gate.test_cache_ttl_s`; a run reads it once, takes a PASS of exactly its key as its own, and publishes the PASSes it adds in one push; a box that cannot read it judges alone; the coverage pass never takes a shared PASS | redesenho | **yes** |
| 1 | A3: Bazel with a remote cache and Gazelle-generated targets | redesenho | no: the same idea (an action cache by input digest) with a build system the engine does not use; the keys already exist |

The main metric's meaning changes and is recorded (D-130): `cold_wall_s` is a box with an empty local store against
the shared results, the box a session, a fresh container or the runner is. The suite run with no store at all is a
new guard, `uncached_wall_s`, never worse.

Commits: (1) this audit and plan and D-130; (2) `scripts/lib/shared_results.py` with its tests; (3) the suite runner
reads and publishes them (`OU_SHARED_RESULTS`, set by `scripts/test-suite`; never seen by a script test; the coverage
pass off); (4) the measurement, ABBA with three repetitions each.

## Painel no fechamento (D-133)
Did the objective improve, or only the number? Only the number with the cache: a fresh box against the shared results
judges in 0.69 s, but the suite with no store at all is still about 96 s on about 320 CPU-s, so the objective (a fast
verdict on any box, with or without kept results) moved for the boxes the cache serves and not at all where it does
not. Coverage, test count and failures held; the e2-micro is not measured. F11 takes the uncached suite.
