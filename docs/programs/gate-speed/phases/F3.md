# gate-speed — F3: ≤ 60 s

Phase 3 of the [solução](../solucao.md) (D-120): the engine's own work under test gets cheap. F2 left the suite at
101.6 s cold on 4 vCPUs and 331.6 CPU-s ([F2](F2.md)).

## Auditoria
What the engine itself spends while the tests drive it, profiled:
1. **The structure check re-reads what it already read.** One run on this repository made about 15,000 registry reads,
   and each read stat'ed the 60 registry files to see whether the memo was still fresh (0.2 ms a read); it judged each
   of 800 parameters' secret shape with seven more reads of the same guard settings; it dated each of 159 plans with
   its own `git log` walk of the whole history; and the literal census walked every syntax tree twice (once for the
   prose to skip, once for the literals). 10.3 CPU-s a run here, about five minutes on the e2-micro, where the stage
   limit is 300 s (D-119). The system that fails: reading a value or a fact is treated as free, so loops repeat reads
   whose answer cannot change inside the loop.
2. **`config.get` copies a whole registry entry to return one value.** Every read deep-copied the entry (schema,
   description, readers) and then returned its default.
3. **The train asks git the same question per step.** A train run read its tooling's version (`git rev-parse
   HEAD:scripts` of the tool checkout) once per batch and verdict: 1,162 git processes in the train's tests for one
   answer per run. The train's test forge read each PR head with a git process per forge read (about 3,100).

| 1 | A2: `config.reading()`, a block in which the registry is stat'ed once; the structure check's tree part runs inside it. One `git log --name-only` dates every plan. One walk of each tree finds the literals and the prose to skip | corrige a classe | **yes** |
| 1 | A3: one parse of each file shared by every check of a run | redesenho | no: it holds every tree at once (+152 MB measured), too much for the e2-micro's 1 GB |
| 2 | A1: read the entry in place and copy only the value returned | corrige a classe | **yes** |
| 3 | A1: memoize the tooling's version per lookup object (one train run, one tooling checkout); the test forge reads a ref's file and asks git only for a packed ref | corrige a classe | **yes** |
| 3 | A2: a batched git reader for every train step | redesenho | later: the train is the merge path; a narrower change first |

Commits: (1) this audit and plan; (2) the structure check and config reads; (3) the train's tooling version and the
test forge's refs; (4) the measurement. Tests: the structure, config, effort, literal and train tests; the whole suite
through `scripts/test-suite --metrics`.
