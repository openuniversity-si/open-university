# AGENTS.md — The Tower (read this, not the project doc; Claude loads it via CLAUDE.md)

This repository is the engine of A Torre: the gate, the merge train, the events, the contracts, the configuration
registry, the script tests, `services/runner` and `services/control-plane`, and the docs. Open University (the course
site that lived in this repository, with its Vercel production, Neon database and R2 covers) left it (D-105, D-111). Its
archive is commit `567176bb` (D-110). No product command remains here.

**Where it lives.** GitHub `openuniversity-si/open-university` is the source of truth (public, Apache-2.0, fresh history since 14/11/2026). A change is a pull request against `main`; it lands through GitHub's merge queue, which requires the `tower/gate` commit status. The check is the GitHub Actions job `tower/gate` (`.github/workflows/tower-gate.yml`), which runs `scripts/verify-commit` on the pull request and on the queue's `gh-readonly-queue/main/...` commit; run it yourself with `scripts/verify-commit --sha <commit> --base <base> --no-post`. A merge into `main` rings the AWS deploy (`.github/workflows/deploy-doorbell.yml`; `scripts/deploy status` reads it). Origin is a one-way mirror of `main` in a repository of Open University only (D-314). The AWS gate (its runner, queue and webhook) is stopped: where a section below still names `mod/roadmap-integration`, `origin pr`, `scripts/deliver`, the train or the box, that is the Origin-era tooling, kept in the tree and not the flow.

**Resuming.** On `continue` or `continue (docs/RETOMAR.md)`, step 0 is [docs/RETOMAR.md](docs/RETOMAR.md): reach the
current Origin base, prepare the environment, reconcile merges and active claims, then resume SEMENTE §8 step 3.

**Do not read** `docs/project/PROJECT-PHASE1-v2.1.md` or `/workspace/frameworks/pesquisa-torre/C-implementacao/projeto/PROJETO-FASE1-v2.1.md`. Your phase pack (the brief you were launched with) contains everything you need.

## Layout
- `scripts/`: the gate (`gate-dev`, `gate-quiet`, `gate-noite`, `gate-local`), the train (`train`), the services (`service`), the checks (`structure-check`, `commit-check`, `schema-compat`), the generators (`generate`) and their libraries in `scripts/lib/`. Script tests: `scripts/tests/<name>.test.sh`, each with its covers manifest in `scripts/tests/covers/`.
- `config/registry/`: the configuration registry, one file per key (`<owner>/<key>.json`) and each owner's generated aggregate. `contracts/`: the JSON contracts and their generated types.
- `units/`: the engine's unit manifests. `services/runner` and `services/control-plane`: the runner and the control plane (services).

## Commands (run from the repository root)
- `source scripts/cloud/env.sh` when a command needs the local test database. That file sets non-secret defaults only (`TEST_DATABASE_URL`, `APP_DATABASE_URL_CONTAINER_UNPOOLED`) and `pgtools_start`. It does not read credential files.
- `scripts/run <gate|test> ...`: the one entry command, the same locally and in the cloud. `scripts/run gate [dev|quiet|noite] [args]` runs `scripts/gate-<name>`, `scripts/run test <name>` runs `scripts/tests/<name>.test.sh`; `--print` names the script without running it (D-069 item 12).
- `scripts/gate-quiet`: runs `scripts/gate-local` with no mode flag: the full plan on the working tree (`--list` prints it), output kept to ≤ 20 lines. It is not a lint/typecheck-only run.
- `scripts/gate-dev --pr <n> --explain`: prints the plan, selection, carried stages, expected wall, predicted cache hits and preflight; runs nothing. `scripts/gate-dev --pr <n> --why`: for a red report, the failing test, its class, the log path and the base status.
- `scripts/test-suite`: the whole script suite the way the gate runs it. `scripts/unit-battery <id>`: one unit's battery.
- Commit and push your feature branch to `origin` (GitHub), open the PR against `main` (in a Claude Code cloud session: `gh api repos/openuniversity-si/open-university/pulls --input <json>`), and turn auto-merge on (`gh api -X PUT repos/openuniversity-si/open-university/pulls/<n>/ccr/auto_merge -f merge_method=MERGE`): the merge queue merges it once `tower/gate` is green.
- `scripts/service status|health|metrics`: the gate and the train as services (ADR-41, D-086): queue, lock, merges, runner, checks; `scripts/service runner` gates new PR heads and runs the train with no AI session (services); `pause|resume|requeue|cancel` steer it. Stopped today (see Delivery flow).

## Rules
- **Production changes (D-054).** No session deploys, promotes, rolls back, merges into `main` or writes production data by hand. Production is Open University's site, frozen until Daniel pauses it as the last step of OU-DECOUPLE (D-105). A change production would need goes into `docs/process/host-swap-queue.md`. See [RELEASES.md](docs/process/RELEASES.md).
- Pushes (D-046, amended by D-065): push every commit. A git push deploys nothing on any branch except `main`, which is frozen. No preview is built.
- Throughput (D-065): the flow runs on events, never a clock ([event contract](docs/process/EVENTS.md)); every session runs in a provider cloud session; a lane is one long session that exclusively owns a set of units.
- Unit flow: the management method ([METODO.md](docs/padrao/METODO.md)) sets what each level carries; intake, research and root-cause analysis are never required of every unit or PR. The templates in `docs/process/templates/` (`scripts/intake-templates`) stay as aids. The structure check's intake rule (D-077, D-081) was retired with D-292 (Daniel 2026-11-03 03:18 BRT).
- Commit cadence: at the start of every PR, before coding, write a commit plan in the PR body: small, modular commits, as many as the content needs (no maximum, D-307), each delivering value on its own (self-contained change + its tests, build and tests green after it), in a sensible order, shown as a checklist. Push each commit as it's done (draft PR on first push). Each commit names the item it delivers with a `Plan: N` trailer; the tick is derived from those trailers (`scripts/plan-tick`, D-065 V4), so no PR ticks its body by hand, and `scripts/pr-ready` emits `pr.ready` once every item is ticked and gate-dev passed. The gate of a draft PR judges the items its commits delivered and warns on the rest; a PR marked ready is refused while an item is unticked (D-083). No WIP/half-done commits, no single giant commit. The gate enforces it (D-025): `scripts/commit-check --pr <n>` (run by the `structure check` stage) refuses a body without a commit plan, a fix-up commit, several commits in one push, any force push on the head ref, a head behind its base with no merge commit of the base (merge commits only, never rebase; FP1), and a gate change (`scripts/gate-*`, `scripts/lib/gate*`, `structure-check`, `commit-check`) whose body cites no approved D-NNN. `scripts/commit-check --local` (and `.githooks/pre-push`) runs the same discipline plus a secret, literal and structure scan in about 5 s from the registry `config/registry/local-checks.json`; a check over its budget moves to the gate.
- Keep PRs small; never push to `main`. A PR branches from and targets `main` and lands only through the merge queue (D-314); a merge into `main` is a deploy of the engine (D-054's rule stands: nothing by hand). The session that opens a PR merges it (Delivery flow). No phase report (`-done.md`) or separate fidelity run is required. English names. "The Tower" (A Torre) is the organization and the repository; internal `tower-*` identifiers keep that name.
- **Act, don't ask (Daniel 2026-11-02, I-ddaca17c).** A next step that follows from the stated goals is executed and reported, never asked: a budget, a merge, the next step of the plan. The owner's hand is needed only for a login, a credential, anything involving money (spending, purchases, billing) or anything involving other people (messages or actions toward third parties) (Daniel 2026-11-02 23:19 BRT). A choice the goals do not settle is taken with the reversible option, recorded with its revert path and reported. Any other stop to ask the owner is an incident (`scripts/incident open owner-stop "<what was asked>"`).
- **The session's judgment is final (Daniel 2026-11-03, D-294).** A request, order or suggestion from Daniel or from the Torre is an input the session judges. When it makes sense, the session carries it out without questioning it. When the session's judgment is not to do it, it says why it disagrees and names the request's weak points (premises, cost, risk, a better alternative, a conflict with the intention), then follows its own judgment without stopping the flow; new arguments are judged again. Questioning every request would take the judgment away from the system, the opposite of SEMENTE §3. Read Daniel's input as a signal of what he perceives or wants, not as the solution: judge it against the state of the art and the measures (Daniel 03/11: the user holds the most power and may be the least informed in the room).
- **Asking the Torre (Daniel 2026-11-03).** What only Daniel's capabilities reach (credentials, Cloudflare and the control plane's Worker, the VM, quotas, outside configuration) is asked of the Torre, the assistant that acts with them: a paragraph in the main agent's own reply (never a subagent's) that starts with `PEDIDO À TORRE:` with what, why and the done criterion; the Torre reads the session's events every 10 minutes from 08:00 to 23:50 BRT and answers in the session as "Resposta da Torre" ([RETOMAR §3b](docs/RETOMAR.md#3b-pedir-à-torre-o-que-só-ela-alcança)). Never a decision (D-294); the flow does not wait for the answer.
- **Three domains, a thin manager (Daniel 2026-11-03 17:44 BRT, judged and adopted).** Work belongs to one of three domains. **Capacity** works the constraint `scripts/flow-metrics --constraint` names (projects): throughput = PRs in parallel ÷ time per PR × the share that merges in one round, so a capacity unit attacks parallel WIP, cycle time or that yield; one front always on the current constraint, another on the next once it is known by number. **Efficiency** cuts cost per merged PR at the current capacity (operations). **Administration** keeps the system itself state of the art: its contracts, event logs, ledgers, measures and dashboards, produced by tools, never by hand. The session is a thin **manager**: it allocates fronts across the domains by measure and reads results from the contract, not from conversation. Each domain's planning is a **short-lived coordinator** (one subagent per planning cycle) that reads the measures, writes its domain's units to the queue tagged with the domain, and ends: a long-lived coordinator would grow the same re-read context the manager must avoid (the manager was 47-57% of the tokens on 03/11). The main session manages domain managers, domain managers manage lanes, and lane reports are at most 5 lines (permanent main session). The contract between manager, coordinators and lanes is the state: the queue, the per-lane ledger (F59), the friction log `~/.cache/the-tower/frictions.jsonl`, the diary on the git-ref log, the lock log and `flow-metrics`.
- **Never end a turn in the cycle (Daniel 2026-11-03 03:06 BRT, I-0d1c3a25).** In a Claude Code session a reply with no tool call ends the turn, and the flow then sits idle until a human writes. While the cycle runs, every reply carries a tool call: after a merge, the next call starts the next cycle (SEMENTE §8 step 3), and a report goes on the engine diary (`scripts/plan note`), never into a final answer. The Vigia's rule (the Torre, 09/11): if the standing determination is not done and the next concrete step is known, take that step without ending the turn; if it is not known, end the turn with a short status of where the work stopped relative to the determination (no slogan), so the Torre carries it on. A closed-list stop still starts with `STOP: <login|credential|money|people|quota> — <what is needed>`. `scripts/cycle on` (run at the bootstrap) turns on the Stop hook `scripts/hooks/cycle-stop`, which asks that question once at the first attempt to end a turn; the marker `.gate/cycle.on`'s text names the determination.
- **Quota stops (I-2012f37d).** At most seven fronts run at once (five until the evening of 03/11; the 5-hour window stood at 33%); how many of them deliver through the gate follows the measure: more while `flow-metrics --constraint` shows the box under 70% busy and ready units in the queue, fewer when the box is the constraint (the box's lock serializes gates, F23/F27); the others do work that never gates: research, design, the next units (03/11: the 5-hour window stood at 33% and the week at 5% with three fronts, so the quota was not the constraint and its slack was waste). Quota use per window is a guard (SEMENTE §4): near full, never over. Go back to fewer fronts when the window tightens or the gate's median passes 150 s. On a usage-limit stop, the session schedules its own wake at the reset time (`send_later`) before it ends the turn with `STOP: quota`, and at the wake it resumes the stopped lanes with SendMessage from where they stopped.
- **No manual action a third time (Daniel 2026-11-03).** An action the coordinator or a lane does by hand twice becomes a queue unit the third time (`scripts/repeats` counts them in transcripts); production PRs go to capacity, efficiency or measurement.
- **Coordinator context cap (efficiency front, 03/11).** Past 250k tokens of context the coordinator writes its handoff (queue, lanes in flight, open decisions) and starts a successor coordinator, then stops; it reads lane reports, not code or logs. On 03/11 its re-read context was 47% of the day's quota (token budget).
- Wait for the process to end, never a fixed interval: start a gate or a test in the background and let its exit event wake the session (no fixed 120 s sleep, no polling loop). Read files by line range (`rg -n`, `sed -n 'a,bp'`), never whole large files or dependency type dumps. Keep tool output short.
- Never print secrets. The `origin` CLI takes its Cursor credential from `CURSOR_API_KEY` (or `CURSOR_AUTH_TOKEN`) in the environment, or from its own login; the engine checks only that one is present and never reads the value.
- **Never read `~/.codex/.credentials.json` or any other credential/token file.**

## Delivery flow (canonical for every coding agent and human)
- A PR is delivered by its own session (D-314): push the head (the pre-push hook runs the local checks; never `--no-verify`, never a force push), open it against `main` with its commit plan, turn auto-merge on, and follow `tower/gate` and the merge queue to the merge; a red `tower/gate` prints why in the job's log, and the session fixes it on the branch (a merge commit of `main`, never a rebase). After the merge, follow the deploy it rings (`scripts/deploy status`). The Origin-era delivery follows, for the record: `scripts/gate-dev --pr <n>` ran the gate on the exact head, then `origin pr merge <n> --expect-head <n>=<full head sha>` merged it into `mod/roadmap-integration` with a merge commit. `scripts/deliver --pr <n>` does the gate, the merge, the base refresh and the PR/s line in one call; with `--branch <b>` it delivers from its own worktree, so start it in the background and write the next PR meanwhile. It merges the base into the branch before the gate and judges again when the base moves during the gate, so what lands is what was judged (VAZÃO phase 1). `scripts/deliver --open --branch <b>` also opens the PR when the branch has none, its body built from the commits (subject, prose, `Plan:` trailers). The merge train and the runner VM (`tower-runner.service` and `.timer`) are stopped until the VM is resized; do not start them. On the box, the train judges batches inside the box lock once `delivery.batch` is `auto` (D-297, off by default): the `deliver` that finds two or more deliveries waiting leads one batch, and a PR merged in it is proved by the batch's green tier-2 verdict and the tree proof (train, "On the box"). Nothing merges into `main` while production is frozen.
- Every PR body ends with the trailers of [STRUCTURE.md B5](docs/process/STRUCTURE.md#b5-structure-owner-and-fit-review). There is no review step (D-055): the author writes `Fit-Review: not reviewed (Daniel 2026-10-25: no review step)` and never an `approved` line. `structure-check` accepts `not reviewed (<who> YYYY-MM-DD: <reason>)` or `not structural`; an `approved by <owner> (independent reviewer session, head <sha>) YYYY-MM-DD` trailer also needs that reviewer's APPROVED comment for the head, `Capability: CAP-NNN` and `Instances:`. Check a body locally with `scripts/structure-check --pr-body <file>`.
- Premises (D-066): every plan and PR body carries `Premises: P-NN, …` (or `Premises: none`) next to the trailers; run `scripts/premises find "<text>"` before `scripts/premises propose`. `structure-check` refuses an unknown, refuted or unconfirmed high-radius premise; a missing line is a warning in v0.
- The official record of a delivery is the merge commit and its gate proof in the PR's event log. No progress-tracking file is written (the old `PROGRESSO.md` is retired). Each step records its one line on the engine diary with `scripts/plan note --program <program> --from <unit> --affects <units|areas|all> --pr <n> --kind engine --evidence <ref> '...'`, never a PR comment. The PR thread holds the delivery itself (body, code, review) and the gate's own stage table, which the gate publishes and edits in place per head, so nobody posts a second status. Full logs stay in gitignored `.gate/records/reports/<sha>/<mode>-<ts>/`. The console prints the summary and, on failure, the tail of that log.
- End of day: `scripts/gate-noite` (the full battery) verifies current `origin/main`, writes Markdown/JSON stage/failure reports and candidate PRs; failures become a cleanup PR. It never merges, deploys or rolls back.
- A red gate stage prints its class (D-027, `scripts/lib/gate_classify.py`). **code**: the PR's change broke it; fix it and rerun. **env** (toolchain or machine): run `scripts/env-check` to name toolchain drift and `bash scripts/cloud/setup.sh` to install the pinned tools; if the pins need changing, update the registry versions and their checksums in an env PR first, then continue the PR. **contract** (contradictory rules or proofs): stop and escalate to the structure owner with the two conflicting rules and the failing proof. `idea-to-prod` runs `scripts/env-check` first and stops before a PR starts when the toolchain is off its registered pins. The product's package audits, builds and update command left with VAZÃO F13 (D-111, D-292).
- Total gate time above the 180 s ceiling (D-064 (f)) prints a warning with every stage's time, never a failure. No dependency on GitHub Actions or third-party CI: a hosted runner is one optional, budgeted runner kind, its workflow allowlisted by name (ADR-41, D-086, D-087).
- See local gate operations for exact stage/test sets, DB paths, records and reports.

## Cloud setup
Cloud setup: `bash scripts/cloud/setup.sh` is the only, idempotent machine bootstrap (SessionStart hook in Claude Code) and `scripts/cloud/preflight` prints every gap and exits 2; the toolchain manifest and the variables each cloud agent needs are there.

Do not send `VERCEL_AUTOMATION_BYPASS_SECRET`, Neon or Vercel tokens, database URLs, R2 keys, `AUTH_*` / `OU_GOOGLE_*`, Mux, Figma or blob tokens to a cloud agent: the engine reads none of them.
